## 3. 必须纠正上一轮交付中的差异

这是本轮复核发现的交付缺口，应由我明确更正：v2 包同时含生产热修复和品牌源码补丁，两条路径没有实现完全相同的行为。源码侧 76 项检查和热修复侧 10 项检查不能相加成“生产全部功能已验证”。

### P1-A：生产热修复创建成功后仍先等待配置接口

线上创建代码顺序仍是：创建接口成功 → 保存 JWT → await getSettings() → 发出 authenticated → 关闭弹窗。

因此创建成功、但 getSettings 网络失败时，弹窗仍不关闭并显示错误。用户可能再次创建邮箱。源码补丁已将“创建成功”和“后续刷新失败”分开，生产热修复尚未同步。

工程要求：

1. 创建接口返回有效凭证后，保存凭证并立即通知父组件关闭创建窗。
2. 绑定账号和刷新信息作为后续操作；失败显示“邮箱已创建，但信息刷新失败”，提供重试刷新。
3. 重试刷新不得再次调用 new_address。
4. 为整个创建操作加独立互斥状态，不能只依靠多个 API 共用的 loading。
5. 模拟创建 200 + settings 500，必须保留凭证、关闭创建窗、只有一次创建请求。

### P1-B：生产删除目标没有在确认窗打开时固定

生产热修复在点击最终确认时读取当前 JWT，并通过 api.fetch 发请求；api.fetch 又在异步指纹采集之后读取全局 JWT。它与源码补丁“确认窗打开时固定目标 + addressJwt 参数”的行为不同。

潜在后果：确认过程中切换邮箱，或另一标签页修改共享的 localStorage，删除对象可能与用户先前看到的目标不一致。现有测试只验证请求等待后不清空新选择，未验证发请求前认证头的目标竞态。

工程要求：

- 打开确认窗时保存 target={address,credential}，展示固定 target.address。
- 点击确认始终使用 target.credential；在指纹采集之前捕获 Authorization 值。
- 若缺少 addressJwt 支持，应补到生产 API 包装器，而不是只在源码补丁里支持。
- 请求成功后仅移除 target 邮箱的缓存；当前选中其他邮箱则保留当前选择。
- 新增真实包装器测试：延迟 fingerprint，修改全局 JWT，断言 DELETE 认证头仍为目标邮箱凭证。

这两项是需尽快修复的残留边界，不能据此宣称已经发生误删。原先正常路径的弹窗/删除接线修复仍有效。

### P1-C：源码基线仍未收敛

品牌 fork 与当前线上仍不等价：fork 的 Index 为 AddressBar+n-tabs，线上是新版首页和收件工作区；Help、Privacy、Tools、SEO 注入也未完整回归。下一轮应提交唯一可重建的生产源码基线。不要再次直接重建 fork 覆盖生产，也不要长期把 minified JS 作为主维护入口。

## 4. 内容炉方案：方向保留，改为有条件推进

同域 `/guide/` 静态文章可以降低对临时邮箱 SPA 的耦合，但“零改动、零风险”应改成“主应用源码可不改，仍有路由、缓存与发布风险”。所有工程说明统一使用 `/guide/`，不要混用 `/guides/`。

### 路由与静态资源合同

- 仅给指南路径添加路由，禁止把整个 mail.jinzhai.icu/* 交给新代理。
- `/guide` 单独规范化跳转到 `/guide/`，保留合理查询参数。
- 文章项目设置 Astro base=/guide；页面链接、JS/CSS、图片、站内搜索、canonical、sitemap 全部验证最终路径。
- 代理是否保留 /guide 前缀必须与实际构建目录一致，不能两边各剥一次或都不剥。
- 原始目标为固定项目域名或绑定，不允许用户通过 query 指定上游地址。
- 404 保持 404；5xx 保持错误状态。源站失败时不得用邮箱首页返回 200 兜底。
- 只承接 GET/HEAD；其他方法明确 405，不让 POST/DELETE 进入内容代理。
- 不向静态文章上游转发 Cookie、Authorization、x-user-token、x-admin-auth 等邮箱认证信息；不把邮箱查询参数传给文章源站。
- 上游响应中的 Location、canonical 不得泄漏 pages.dev 地址；文章页返回公共 mail.jinzhai.icu URL。
- 不给邮箱 API 套用文章缓存策略。HTML 用可控短缓存或再验证，带内容指纹的资源可长缓存。

Cloudflare 官方路由文档说明最具体的匹配路由优先。必须先导出现有路由和绑定，验证新增指南路由与当前 Pages 自定义域名的组合；“写几十行代理就零风险”不足以验收。

### 发布与回滚必须隔离

文章发布只能更新独立 mail-guides 项目，不能复用主站 tempmail 的上传脚本。否则一次文章发布可能覆盖整个邮箱站。

首选 robots 同时列出主站 sitemap 和指南 sitemap，让两套 sitemap 各自维护。不必每发一篇文章就重传整个主站。若选择 sitemap-index，需明确旧 sitemap 文件如何保留及所有索引 URL 的公开地址。

一次性更新主站 robots 时必须从当前生产制品进行版本化合并，保留已上线的热修复及所有资源；不能拿旧 live-dist 重传。生产内容清单记录 site_id、project_name、domain、base_path、deployment_id、内容版本。部署脚本在项目不匹配时直接拒绝。

摘路由只能回滚路由层，不会回滚 robots、缓存和已发布文章；三项分别记录恢复办法。

## 5. 内容生产规则需调整

保留中文首批 5 篇人工审校，但不要规定“每天必须 2 篇”。建议 14 天内最多 28 篇，资料不足时跳过，失败入草稿。主题意图与 freessl、其他邮箱相关文章做全局去重；不同站换标题不算独立选题。

首批建议：

| 主题 | 独有证据 | CTA |
|---|---|---|
| 首次使用与保存凭证 | 当前真实界面和操作步骤 | 创建测试邮箱 |
| 收不到验证码如何排查 | 实测送达、域名限制与延迟说明 | 返回收件箱/尝试新地址 |
| 删除邮箱、解绑与本机移除的区别 | 三条真实代码路径 | 管理当前邮箱 |
| 临时邮箱适用边界 | 找回账号风险、不可替代重要个人邮箱 | 查看使用说明 |
| 邮箱别名与临时邮箱如何选择 | 可核对的功能差异 | 选择适合的方案 |

“有效期/续期”“安全匿名”“毫秒级送达”等内容必须由当前环境配置、清理任务或实际测量支持。无证据时说明未确认，不自行编造 TTL、成功率和留存天数。

删除、数据保留、隐私说明类文章需要人工审核；竞品对比记录来源与核对日期。内容炉不读取真实邮件正文、地址凭证或验证码作为文章素材。

## 6. SEO 与 GEO 的两项更正

1. FAQ 正文可以保留以帮助用户，但 FAQ schema 不应成为本项目的 Google 增长卖点。Google 官方更新记录说明 FAQ 富结果已从 2026-05-07 起不再显示，6 月移除了对应功能文档。可用 Article/BreadcrumbList 等适合页面内容的标记，不能保证展示。
2. 开头直接回答有阅读价值，但不保证被 AI 引用。应提供真实步骤、截图、出处、更新日期与明确限制，而不是只优化成容易摘录的模板。

子域名“权重独立、对主域加成弱”也不宜写成确定的排名公式。选同域路径主要基于品牌、导航、发布和归因便利，而不是承诺 SEO 权重自动合并。

## 7. 转化设计：不要停在 CTA 点击

原方案“文章→主站 ≥3%”只能说明导流，不是创建邮箱成功。分两层统计：

| 指标 | 分子/分母 | 用途 |
|---|---|---|
| 导流点击率 | 点击 CTA 的去重文章会话 / 合格文章会话 | 检查内容与入口 |
| 创建启动率 | 触发创建动作的文章归因会话 / 合格文章会话 | 检查落地衔接 |
| 创建成功率 | API 返回有效凭证的文章归因会话 / 合格文章会话 | 产品主指标 |
| 创建流程成功率 | 创建成功 / 创建尝试 | 区分流量问题与功能问题 |

合格会话排除已知机器人、内部验收及重复刷新。属性仅含 article_id、intent_id、cta_position、campaign、错误类型等，不含邮箱、JWT、邮件正文、验证码或可携带凭证的完整 URL。UTM 只携带非敏感归因值。

当前静态站零源码改动可以测 CTA 点击，但要可靠测创建成功，必须补充主站成功事件或隐私安全的产品统计通道。因此“零主站改动”与“完整创建转化验证”不能同时直接成立。主站尚未接成功事件时，报告只写导流点击，不假称建址转化。

## 8. 试验节奏和判定

- D0–D2：先修复生产两处边界、确认版本证据，完成指南路由和资源/404 测试。
- D3–D5：发布 5 篇经审校的样板，接通 CTA 和创建成功统计。
- D6–D14：按实际选题质量补充，最多至 28 篇；没有资料不补数量。
- D28：检查抓取/索引、搜索曝光、合格会话与创建成功，不自动放量。
- 若合格文章会话不足 200，3% 点击率样本过小，标记为证据不足，继续观察而非判输赢。200 为本次管理建议，不是统计显著性的保证。
- 索引率按已发布满 14 天且确实可索引的 URL 计算，避免把刚上线文章纳入同一分母。
- 索引不足先排查 404、canonical、源站、内容相似度和内链，再暂停新增；不要到 D28 不达 50% 就永久不维护。
- 达到观察目标后先改善实际创建成功和留存，再决定是否增加频次或英文试点。
